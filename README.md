# 宿藤家居 ERP

库房仓储管理工具。只记数量，不记价格。

- 技术栈：Next.js 15（React 19）+ TypeScript + Prisma + SQLite + Tailwind
- 部署形态：单进程 + 单文件数据库，适合仓库小主机 / NAS
- 访问方式：局域网 `http://<主机IP>:3000`，手机与电脑同一套界面

## 本机启动

```bash
cd suteng-erp

# 1. 安装依赖
npm install

# 2. 准备环境变量（首次）
cp .env.example .env
# 编辑 .env，至少改 JWT_SECRET：
#   node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

# 3. 建库并写入初始数据
npm run db:migrate
npm run db:seed

# 4. 启动
npm run dev          # 开发（带热更新）
# 或
npm run build && npm start   # 生产
```

打开 http://localhost:3000

**初始账号**：`admin` / `suteng@2026`（来自 `.env` 的 `BOOTSTRAP_ADMIN_*`）
**第一次登录后请立刻改密码** —— 目前还没有改密码界面，先用接口：

```bash
curl -X PATCH http://localhost:3000/api/auth/password \
  -H "content-type: application/json" \
  -b cookies.txt \
  -d '{"currentPassword":"suteng@2026","newPassword":"你的新密码"}'
```

## Docker 部署

> **完整教程见 [`DEPLOY.md`](./DEPLOY.md)**（准备工作、两条部署路线、验收清单、运维命令、排障表、安全清单）。
> 下面只是最简版。

镜像已发布：`aag111/suteng-erp:latest`（`linux/amd64`，含 `vYYYYMMDD` 日期标签）。
compose 里同时有 `build: .` 与 `image:` —— 源码构建会打上这个 tag；
只想跑现成镜像时删掉 `build:` 那行，`docker compose up -d` 就会去 Hub 拉。

```bash
# 1. 在项目根目录建 .env（只放 compose 用的变量）
cat > .env <<'EOF'
JWT_SECRET=换成随机串，node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
HOST_PORT=3000          # NAS 上若 3000 被占用就改成别的（如 3080）
BOOTSTRAP_ADMIN_PASSWORD=首次启动时的管理员口令
EOF

# 2. 构建并启动
docker compose up -d --build
```

容器启动时会自动依次执行 `prisma migrate deploy` → `node prisma/seed.mjs`（建管理员与
主仓 / 次品区 / 报废区三个仓位）→ `node server.js`，所以首次部署不需要手工进容器敲命令，
重启也不会重复建。初始化是幂等的：已有用户就跳过，不会覆盖已改过的密码。

数据保存在宿主机 `./data/`，容器重建不丢。

> **不要把 `data/` 放在 SMB / 网络共享盘上**，SQLite 的锁在网络盘上不可靠，会偶发写坏。
>
> **不要直接 `cp` 运行中的 `suteng.db`**：WAL 模式下来不及落盘的事务还在 `-wal` 里，
> 拷出来会静默少几笔。备份走「备份」页的「立即备份」（内部 `VACUUM INTO`），或先停容器。

### 构建期的坑（都已处理，改 Dockerfile 前先读）

1. `next build` 会加载每个 API 路由做静态分析，而 `env.ts` 在模块加载时就要校验配置。
   构建容器里没有运行期变量，所以 builder 阶段注入了**假的占位值**
   （`DATABASE_URL` / `JWT_SECRET`），仅用于让构建通过；运行期由 compose 注入真实值。
2. `COPY --from=builder /app/public ./public` 要求源码存在 `public/`，没有静态资源也要保留
   （当前用 `public/.gitkeep` 占位）。
3. **构建阶段必须用 `node:22-bookworm` 完整版，不能换 slim。** Prisma 靠 `openssl` 命令
   探测 libssl 版本，slim 里没有，会把平台判成 `debian-openssl-1.1.x`，生成的引擎和
   运行镜像（3.0.x）对不上，启动报 `could not locate the Query Engine`。
4. **运行阶段要把 `openssl` 拷进镜像。** 运行时也要探测平台，缺了同样判错。
   因为内网 NAS 解析不了 `deb.debian.org`（apt 装不了），Dockerfile 直接从 builder
   拷 `/usr/bin/openssl` 与 `libssl.so.3` / `libcrypto.so.3`（同版本 Debian，ABI 一致）。
5. 不要在 `schema.prisma` 里写多个 `binaryTargets`：会触发联网下载引擎，
   而内网常解析不了 `binaries.prisma.sh`，构建直接失败。只留 `native`。
6. **运行阶段一个包都不许联网装**（2026-10-23 踩的）。原来 `RUN npm i -g prisma@6.16.2`
   能过，纯粹是吃了 Docker 层缓存；P11 改了 `prisma/` 目录（加迁移），缓存作废，
   这一层重新执行时 `getaddrinfo EAI_AGAIN registry.npmjs.org` 直接构建失败——
   NAS 的构建容器**连 npm registry 的 DNS 都解析不了**（实测 `getent hosts` 无结果）。
   现在改成 `RUN node scripts/bundle-prisma-cli.mjs` 在 builder 里把 CLI 的依赖闭包
   （34 个包、约 200 MB，含 linux 原生引擎）拷成 `/prisma-cli`，运行阶段 `COPY` 过来，
   全程离线、版本与构建期完全一致。**以后往运行阶段加任何 `npm i` / `apt install`
   都是同一个雷**：本地有缓存看不出，哪天上游目录一变就炸。
7. `fs.cpSync` 在 Windows 上拷 `node_modules/prisma` 会把 node 进程打死
   （无任何报错、退出码 127）。`bundle-prisma-cli.mjs` 因此手写递归拷贝，
   在容器（Linux）里跑反而没这个问题——但脚本要保持手写版本，因为本机也要能试跑。

### 部署到 NAS（当前在用的就是这套）

- 目录：`/opt/suteng-erp`（数据在 `/opt/suteng-erp/data`，容器重建不丢）
- 端口：`3080`（`.env` 里 `HOST_PORT` 控制）
- 访问：`http://192.168.1.110:3080`

日常更新一条命令（会打包、上传、重建、健康检查）：

```bash
set NAS_SSH_PASSWORD=你的SSH密码
python deploy/update-nas.py
```

手工更新则是：把源码同步到 `/opt/suteng-erp`（保留 `data/` 与 `.env`），然后

```bash
cd /opt/suteng-erp && docker compose up -d --build
```

容器带 `restart: unless-stopped`，NAS 重启后会自动拉起；前提是 Docker 服务本身开机自启。

### 发布镜像到 Docker Hub

镜像已上传：`aag111/suteng-erp`，标签 `latest` + 构建当天的 `vYYYYMMDD`。

**为什么不在 NAS 上直接 `docker push`**：NAS 上 `registry-1.docker.io` 被 DNS 污染
（解析到 `199.96.62.75`），443 也不通，`dockerd` 根本出不去。所以走「**NAS 导出 → 本机推**」：

```bash
# 1) NAS 上导出（root 属主，要用 sudo）
ssh -p 22033 admin@192.168.1.110 \
  "echo <密码> | sudo -S sh -c 'docker save -o /tmp/suteng-erp.tar suteng-erp-erp:latest && chmod 644 /tmp/suteng-erp.tar'"

# 2) 把 tar 拉回本机（SFTP，实测 75 MB/s，830MB 约 11 秒）

# 3) 本机推上去（本机不需要装 Docker，crane 是单文件 Go 程序）
MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL="*" \
  "<venv>/Scripts/python.exe" deploy/push-local.py \
  --username aag111 --token 'dckr_pat_...' \
  --image suteng-erp --tarball 'C:\path\to\suteng-erp.tar'
```

脚本会自己决定走不走代理（`--proxy auto`，默认）：直连能到 registry 就直连，不通才起
本机 HTTP CONNECT 代理转 SOCKS5（Go 程序不认 `socks5://`，只认 `http://`）。
推完补 `vYYYYMMDD` 标签并回查 digest。

`crane.exe` 放在 `.tools/`（脚本默认去那儿找），换机器重新下：
`go-containerregistry` releases 里的 `Windows_x86_64`。

**两个坑**：
- `crane tag` 第二个参数只收**标签名**，传 `aag111/suteng-erp:v20261021` 这种完整引用会被
  当成 tag 字符串拼进 URL，报 `404 page not found`。
- `docker save` 出来的 tar 属主是 root，普通用户 rm 不掉，清理要加 `sudo`。

## 配置项

全部来自环境变量，启动时集中校验，缺一项直接起不来（避免带病运行）。

| 变量 | 说明 | 默认 |
|---|---|---|
| `DATABASE_URL` | SQLite 路径，相对 `prisma/` 目录 | `file:../data/suteng.db` |
| `JWT_SECRET` | 令牌签名密钥，**至少 32 位随机字符** | 无（必填） |
| `ACCESS_TOKEN_TTL` | 访问令牌有效期（秒） | 28800（8 小时） |
| `REFRESH_TOKEN_TTL` | 刷新令牌有效期（秒） | 6048000（70 天） |
| `UPLOAD_DIR` | 商品图片目录，支持绝对路径 | `./data/uploads` |
| `UPLOAD_MAX_MB` | 单张图片上限 | 5 |
| `BOOTSTRAP_ADMIN_*` | 首次建库时的初始管理员 | admin / suteng@2026 |
| `LOG_LEVEL` | 日志级别 | info |

### UPLOAD_DIR 怎么自定义（docker 部署）

`UPLOAD_DIR` 是**容器内**的路径，不是宿主机路径。想让它落到宿主机某个磁盘上，
必须再有一条 `volumes` 把那个宿主机目录接到这个容器内路径上，两处要一致：

```yaml
    environment:
      UPLOAD_DIR: "/app/uploads"                  # 容器内，随便取名，只要和下一行对上
    volumes:
      - ./data:/app/data                          # 数据库照旧
      - /data/suteng/uploads:/app/uploads         # 图片真正落地的地方
```

只改 `UPLOAD_DIR` 不配 `volumes`，容器会在自己那层新建一个空目录——宿主机上永远看不到
图片，重建容器（`pull` 后 `up -d`）就全没了，而且没有任何报错。

相对路径相对的是容器工作目录 `/app`，所以默认值 `./data/uploads` 等价于
`/app/data/uploads`。**建议一律写绝对路径**，省得自己算。

改路径之后老图片不会自动跟过去，要手工搬（否则历史图片全部 404）：

```bash
mkdir -p /data/suteng/uploads
docker cp suteng-erp:/app/data/uploads/. /data/suteng/uploads/   # 从旧位置捞出来
docker compose up -d --force-recreate
```

⚠️ 从 v1.5 起系统备份**已经把图片一起打进包里了**（`suteng.db` + `uploads/` + `manifest.json`），
所以图片目录挪到哪儿都不影响「用备份页恢复」；但「直接拷 `data/` 目录」这种土办法仍然要求
图片在 `./data` 下面，否则拷走的不带图。图片目录也不要放 SMB／NFS 网络盘。

## 鉴权说明

- 访问令牌与刷新令牌都放在 **httpOnly Cookie**，不进 localStorage、不进 URL。
- 访问令牌 8 小时；过期后由 middleware 自动用刷新令牌换新，用户无感。
- 刷新令牌**轮转**：每次使用即作废并换新的，泄露也只能用一次。
- Cookie 的 `secure` 固定为 `false`：本系统走局域网 HTTP，设为 `true` 浏览器会直接拒绝保存 Cookie，登录会失效。将来接入 HTTPS 时再改。
- 登录失败 5 次锁 60 秒（单进程内存计数）。

## 已完成的功能

**商品管理**
- 一个产品下按颜色分行，一色一个 SKU；不同颜色库存独立（P2 接入流水后生效）
- 颜色行选「定制」即定制款：按件追踪、退货不可回良品
- 数量单位按商品自选：件 / 把 / 张 / 套
- 拼音搜索：中文 / 全拼 / 首字母（`boby` → 北欧布艺单人椅），前缀命中优先、常用款靠前
- 拼音索引在保存时生成并落库（不是查询时现算）
- 同名产品冲突提示「是否直接加颜色」
- 未传图标记「待完善」，列表顶部提示补全
- 图片上传（JPG / PNG / WebP ≤ 5MB），读取需登录

**入库**
- 建单：搜名称或拼音首字母 → 回车加行 → 填数量 → 保存；一色一行，同款多色分行
- 单据两种状态：草稿（不影响库存）/ 已生效（生成流水）。默认「保存并审核」一步到位
- 生产日期选填：填了按「颜色 + 生产日期」自动归批（批次号 `P20261001`），只用于追溯
- 定制款按件追踪：审核时为每一件生成唯一编号 `DZ-20261020-001`，无需贴物理标签
- 单号自动生成 `RK-20261020-001`，按业务日期分段，删过草稿也不会重号
- 补录：业务日期可改成昨天，流水时间跟着走（账记在那一天，不是提交时间）
- 草稿可删；已生效不能删（红冲功能待开放），原始记录永久保留
- 入库页可直接「新建产品」，复用的是商品页同一张表单，建完自动加进本单

**出库**
- 建单：搜名称或拼音首字母 → 填数量 → 保存；常规款填数量，定制款勾选具体哪一件
- 单号 `CK-20261020-001`，同样按业务日期分段、草稿可删、审核才扣库存
- **库存不足会拦单**：审核时按「同一颜色合计」校验，报错直接指出哪一行少多少
- **批次自动扣减**：默认按生产日期先后从最早批次扣（不拦发货，只把账记准），也可手动指定某一批
- 一行跨多个批次时，会按批次拆成多条流水，批次余量始终与库存一致，详情页显示实际扣减批次
- 定制款必须点选具体单件（不接受按数量扣），审核后该件状态变「已出库」，可反查来源入库单
- 草稿阶段就锁定选中的单件：同一件不会被两张单抢走；删草稿自动解锁
- 记录淘宝订单号 / 收件人 / 物流单号，列表与详情都能按订单号、物流单号反查
- 已生效不能删（红冲待开放），草稿可删

**退货**
- **必须先选原出库单**：搜单号 / 淘宝单号 / 物流单号 / 产品名，草稿出库单不出现在候选里（货没发出去，退不了）
- 退货明细挂在**原出库行**上，系统按行校验「本次退 + 之前已退 ≤ 原单已发」，多退的直接拦下并说明还剩多少
- 单号 `TH-20261020-001`，同样按业务日期分段、草稿可删、审核才动库存
- **三个去向**：良品回架（进主仓，可售库存 +）、次品区（不计入可售）、报废（进报废区）
- **定制款只允许次品区 / 报废，不能回良品架** —— 后端硬校验，改前端也绕不过去
- 定制件退货必须**勾选具体哪一件**（按件管理），审核后该件状态从「已出库」变「次品区 / 已报废」并落到对应仓位
- 良品回架会**把数量加回原批次**（取原出库行扣减的首个批次），批次余量与可售库存始终一致
- 次品 / 报废**不进批次**：批次只跟「可售可出」的量走，避免批次余量虚高
- 草稿阶段就锁定选中的定制件，同一件不会被两张退货草稿抢走；删草稿自动释放
- 原出库行累计已退数量（`document_items.returnedQty`）是「已退 ≤ 已发」的唯一依据，跨退货单累加

**盘点**
- **一张单盘一个仓位**（主仓 / 次品区 / 报废区），选仓位 + 截止时点，系统列出账面数，只填实盘数
- **不停业盘点**：账面按「截止时点之前录入的流水」冻结，之后发生的发货、入库算「截止后变动」，
  单列一列显示，不影响这次盘点的差异，也不要求先停发货
- 单号 `PD-20261020-001`；差异 = 实盘 − 账面，正数盘盈、负数盘亏，实时标色
- 「按账面一键填充」：绝大多数款没差异时，一次填满，只改有差异的那几行
- **账面上有货的款必须都盘**（审核时重算核对），漏盘直接拦下并报出是谁、账面多少——
  不然少的货没人知道
- **常规款**：盘盈归到 `PD-日期` 批次；盘亏按生产日期先后扣批次，批次余量与库存始终一致
- **定制款**：盘亏必须勾到具体件，审核后该件状态变「盘亏」、仓位清空；盘盈直接拒绝（每件都有编号）
- 草稿阶段锁住判为盘亏的件，出库侧看不到也发不出去；删草稿自动释放
- 同一仓位同时只允许一张盘点草稿（两张草稿各调一次，差异会算两遍）
- 差异流水 `bizType = 'stocktake_adjust'`，时间锚在截止时点，仪表台的本月出入库不会被它污染

**仪表台**
- 四个核心数字：当前在库 / 本月入库 / 本月出库 / 本月退货（全部由流水推导）
- 商品概况：产品数、颜色行数、分类数、待完善数
- 最近操作（来自审计日志）

**库存（/inventory）**
- 四个视图：按款汇总 / 批次明细 / 定制件台账 / 库存流水
- 按款汇总一个颜色一行，可售、次品区、报废区分列显示；低于安全库存打「偏低」标
- 批次明细按生产日期排，账龄超 90 天标红
- 定制件台账：件号、状态、所在仓位、从哪张入库单来、发给哪张出库单，全程可查
- 库存流水：按类型 / 日期筛选、分页；红冲的反向流水带「红冲」标，与原始流水并排列出
- 支持搜索商品 / 颜色 / 单号 / 件号 / 批次号

**报表（/reports）**
- 四个核心数字：本月入库 / 出库 / 退货 / 损耗，各带「较上月同期」变化
- 近 12 个月出入库柱状图（纯 CSS 绘制，不引图表库）
- 本月损耗按款拆分、按处置方式拆分（转报废 / 线下出售 / 自行处理各占多少）
- 次品区：在区件数、本月流入、本月处置、消化率
- 批次账龄分五档：30 天内 / 31–60 / 61–90 / 90 天以上 / 无生产日期
- 低库存预警（只提醒设了安全库存的款）
- 单据作业量：各类型单据的已生效 / 草稿 / 已作废张数

**导出**
- 六种 CSV：库存明细、批次明细、定制件台账、库存流水、单据清单、损耗台账
- 统一带 UTF-8 BOM，Excel / WPS 双击打开不乱码；文件名带日期
- 导出的是「当前筛选条件下的全部行」，不是当前页

**账号管理（/users，仅管理员）**
- 新增账号、改姓名、改角色、停用/启用、重置密码
- 四道防锁门：不能停用自己、不能降级自己、不能停掉最后一个可用管理员、不能给自己走「重置密码」
- 改密码 / 重置密码 / 停用后，旧访问令牌立即作废（不是等它过期）
- 只能停用不能删除：单据上的经手人名字要留着
- 右下角头像旁有「修改密码」，需要先输原密码

**商品图预览**
- 商品列表、入库选品、出库选品、单据行里的商品缩略图，鼠标悬停即弹出大图（340×300，object-contain）
- 点一下缩略图也能开关（触屏设备没有 hover）；滚动 / 缩放 / Esc 自动收起
- 浮层用 portal 挂到 body，不受表格 `overflow-x-auto` 裁剪

**入库单删除（仅管理员）**
- 草稿与已生效都能删；普通账号连草稿也删不了（前端只显示「找管理员删」，接口 403）
- 已生效单删除 = 彻底删除：批次余量扣回、定制件编号删除、流水与单据一并清掉，库存回到入库前
- 四道校验：只认入库单 / 货还在仓里 / 件没被别的草稿占用 / 批次余量够扣
- 需要留痕的更正请走红冲，两者在详情页并排给出

**保存二次确认（入库 / 出库）**
- 点「保存并审核」或「存为草稿」先弹确认框，逐行列出产品·颜色×数量、业务日期、仓位
- 出库额外显示淘宝订单号 / 收件人；没填订单号会提示「以后退货找不回这张单」
- 任一行数量 ≥ 100 会醒目提示「多打一个 0 是最常见的错」

**数据备份与恢复（/backups，仅管理员）**
- 手动备份：随时点「立即备份」，永不参与轮转
- 定时备份：用 **cron 表达式**定时间（`0 3 * * *` 每天 3 点、`0 */6 * * *` 每 6 小时、
  `0 3 * * 1` 每周一），界面给 6 套常用预设 + 实时显示「下次运行」；按份数轮转旧的自动备份，错过会补跑
- 备份包 = `suteng-<kind>-<时间戳>.tar`，里面三样：`suteng.db`（`VACUUM INTO` 一致性快照）、
  `uploads/`（全部商品图）、`manifest.json`（时间 / 库大小 / 图片张数）。不压缩，7-Zip 可直接打开
- 云端备份：开启后每次备份完成自动把整个包上传；**支持 OpenList 与坚果云（WebDAV）**两家，
  失败不影响本地备份，列表里点云朵图标可重传；「测试连接」可先验证地址/目录/权限（坚果云会真写一个探针文件再删）
- 坚果云填法：地址 `https://dav.jianguoyun.com/dav`，账号 = 注册邮箱，
  密码 = 网页版「设置 → 安全选项 → 添加应用密码」生成的那一串（**不是登录密码**）
- 备份文件可下载到本机（流式，几百 MB 也不吃内存）；列表显示类型、格式、图片张数、大小、时间、是否已上云
- 恢复有两个入口：列表里点某行的「历史」图标直接退回去；或上传一份包（换机器时用）。

- 恢复图片是**只补不删**：包里有的图按文件名补齐，已存在的同名图跳过，现有图片一张不删；
  恢复完会报「包里有几张 / 补了几张 / 还有几个商品找不到图」
- 老格式 `.db` 备份仍可下载与恢复，但**不含图片**，界面会明确提示

## 库存铁律（改代码前务必先读）

1. **没有任何「当前库存」字段可写。** 库存 = `stock_movements.qtyDelta` 求和（按仓位过滤）。
   想改库存只有一条路：开单据 → 审核 → 生成流水。错账靠红冲，不靠改数字。
2. **单据审核才生效。** 草稿不产生流水，库存数字不动。
3. **流水时间 = 单据业务日期**（`occurredAt`），不是写入时间。补录昨天的发货，账就记在昨天。
   唯一例外是盘点调整：它的 `occurredAt` 锚在「截止时点」，见第 11、12 条。
4. **常规款按数量 + 批次，定制款按件。** 两条轨道汇入同一张流水表：
   定制件一条流水对应一件（`itemInstanceId` 有值），常规件一行一条（`qtyDelta = qty`）。
5. **次品区 / 报废区不可售**，不进「当前在库」；它们单独统计，也不会被入库单直接写入。
6. **出库按批次扣减，不按 SKU 一刀切。** 一行可能跨多个批次，因此一条明细可能对应多条流水；
   `batches.quantity` 随审核递减，出库单行的 `batchNo` 只是「实际扣了哪批」的展示缓存，真相仍在流水。
7. **定制件出库必须锁定到具体单件**（`item_instances.outboundItemId`）。草稿即锁定，
   避免两张单抢同一件；件出库后 `status=outbound`、`locationId` 置空。
8. **退货必须挂原出库单**（`documents.originDocumentId`），明细挂原出库行
   （`document_items.originItemId`）。「已退 ≤ 已发」按原出库行的 `returnedQty` 累计，
   不按 SKU 全局统计——否则同色多行的额度会互相串。
9. **定制款退货不允许回良品架**（后端硬校验）。定制规格退回来卖不掉，
   让它回良品就等于给可售库存注水；只能 `defective` / `scrap`。
10. **退货流水一律 `bizType = 'return_in'`，正数**；去向靠 `locationId` 区分：
    主仓 = 可售回架、次品区 = 不可售、报废区 = 报损。次品/报废不增加批次余量。
11. **盘点账面按「录入时间」截断**：账面数 = `stock_movements.createdAt <= documents.snapshotAt`
    的合计，**不是按 `occurredAt`**。业务日期只到天，晚上九点发的货 `occurredAt` 会落在当天零点，
    一混就把截止后的出库算进账面。`createdAt` 写入后永不改动，所以基数天然冻结——
    建单之后才有的一切流水都进不了账面，只能算「截止后变动」。**盘点期间照常发货、照常入库。**
12. **盘点差异流水 `bizType = 'stocktake_adjust'`，`occurredAt` 锚在截止时点**，`qtyDelta = 实盘 − 账面`。
    这样截止之后发生的出入库会**叠在修正后的基数上**，而不是被这次修正冲掉。
    仪表台「本月入库/出库」只统计 `inbound` / `outbound`，不会被盘点调整污染。
13. **一张盘点单只盘一个仓位，同一仓位同时只允许一张草稿。** 两张草稿按同一个账面各调一次，
    差异会被算两遍。审核时还会重算「账面不为零的款」，盘点单漏了谁直接拦住——
    否则少掉的货没人知道。
14. **盘点差异怎么落批次**：常规款盘盈归到 `PD-日期` 批次（盘出来的货没有生产日期），
    盘亏按「先产的先走」扣批次，批次不够扣的部分走无批次流水；**次品区 / 报废区不碰批次**。
    **定制款盘盈一律拒绝**（每件都有编号，账上没有的件不会凭空出现），**盘亏必须勾到具体件**
    → 该件 `status='missing'`、`locationId` 置空，并写 −1 流水。草稿阶段就锁住这件，
    删草稿自动释放；被盘点草稿锁住的件在出库侧看不到、也发不出去。
15. **红冲 = 补一套反向流水，绝不删改原流水。** 反向流水沿用**原 `bizType`**、数量反号，
    并带 `reversal = true`。两个后果都是想要的：
    - 库存是求和，账自然退回去；
    - 「本月入库/出库」按方向取绝对值统计，反向流水不会把历史数字抵消掉
      —— 8 号确实入过 10 件，这个事实不因为后来冲单而消失。
    冲单前读原流水必须 `where reversal = false`，否则冲第二次会把上次的反向也一起冲掉。
16. **红冲的四种前提（冲不动就整单回滚，不留半截账）**：
    入库 —— 货必须还在该仓位（含批次余量够、定制件仍 `in_stock` 且未被任何草稿占用）；
    出库 —— 单上不能挂着未作废的退货单（退货的「已退」算在原行上，单先废了锚点就丢了）；
    退货 —— 去向仓位要扣得回来，件若已被线下出售/处置则要求先冲那张处置单；
    处置 —— 货退回报废前的仓位，报废区那一条也要扣回来。**盘点单一律不许红冲**（再盘一次才是更正）。
17. **处置单三种方式在账上的唯一区别：货还在不在仓库。**
    `scrap` 转报废写两条流水（源仓位 −N、报废区 +N），件 `status='scrapped'` 且仍在报废区；
    `offline_sale` / `self_dispose` 只写源仓位 −N，件 `status='sold_offline' / 'disposed'`、`locationId` 置空。
    可售仓位出货时按「先产的先走」扣批次；次品区本来就没有批次。定制件一律按件勾选。
    次品区**不提供「改判回良品架」**——那是给「把次品当好货发出去」开后门。
18. **报表有两种口径，别混在一起看**：
    - **作业量**（本月入库 / 出库 / 退货）= 流水按方向取绝对值。红冲补的是反向流水，
      不会把「8 号确实入过 10 件」这个事实抵消掉。
    - **业务结果**（本月损耗、次品区消化）= 有效的报废处置单明细。单据被红冲后
      `status = 'voided'` 自动排除——冲掉的那张单不该继续算在损耗里。
    同比一律跟**上月同期**（上月只取到同一个日号）比，不跟上月整月比：月初看整月比永远是暴跌。
19. **改密码 / 重置密码 / 停用，旧会话必须立刻失效。** 只撤 refresh token 不够——
    手里那张还没过期的 access 令牌照样能进门。所以 `users.passwordChangedAt` 记下变更时刻的
    **毫秒戳**，签发令牌时把它写进 `pwd` 声明，`getSession` 拿令牌里的值与库里的值比对，
    不一致就当未登录。**不要改成拿 JWT 的 `iat` 去比**：`iat` 只到秒，
    「重置密码」与「旧令牌的下一个请求」可能落在同一秒里，比不出先后（第一次实现就是这么翻车的）。
    `isActive=false` 同样在 `getSession` 拦死；角色与姓名也每次从库里取，改完立刻生效。
20. **入库单的删除只给管理员，而且「彻底删除」不是红冲。** 权限在路由层收口
    （`roles: ["admin"]`），前端按角色只决定显不显示按钮。语义区别：
    - 红冲 = 留痕更正：原单还在、反向流水并排留着，账对了但记录不消失；
    - 彻底删除 = 当作没录过：单据、明细、它产生的流水一起删掉，批次余量扣回、
      定制件编号一并删除，单号腾出来，「本月入库」也不再算这一笔。
    删除前必须过四道校验（只认入库单 / 货还在仓里 / 件没被别的草稿占用 / 批次余量够扣），
    一条不满足就整单不动。删除动作本身写审计日志——「记录消失」这件事也要留痕。
21. **备份 = 整库快照 + 全部商品图片，打成一个 `.tar`，不做 JSON 导出导入。**
    单据、明细、批次、单件、流水之间有几十条外键，导出成 JSON 再导回来，一旦顺序或字段对不上，
    库存就会**默默算错**；整库快照是唯一能保证「恢复完和备份那一刻一模一样」的做法。
    库用 SQLite 的 `VACUUM INTO`（一致性快照），失败才退回「先 checkpoint 再拷文件」。
    **图必须一起备**：库里 `products.imageUrl` 存的是 `/api/files/<uuid>.jpg`，
    只备库不备图，换台机器恢复完账是对的、商品图全是破图（客户真实踩过）。
    包里固定三样：`suteng.db`、`uploads/*`、`manifest.json`。不压缩（图片本来就压过），
    7-Zip 双击就能看。**tar 是自己写的**（`modules/backup/tar.ts`，ustar，~300 行）：
    NAS 构建容器连不上 npm registry，`tar` / `archiver` 这类依赖装不进去，也不能为它开这个口子。
22. **手动备份永不参与轮转。** 份数限制（`backup.keepCount`）只作用于定时备份
    （`suteng-auto-*`），`suteng-manual-*` 与 `suteng-pre-restore-*` 攒多少留多少，
    要清理由管理员点删除——手动备的那一份是出事后的唯一指望，谁也不能把它挤掉。
23. **恢复数据是整库覆盖，覆盖前先拍 `pre-restore` 快照。** 这是全系统唯一会让数据「变少」的动作，
    所以只给管理员；只认 tar（含 `suteng.db`）或 SQLite 文件头，且必须能读出
    `products / documents / users / stock_movements`，否则直接拒绝；拍不出保命照就不许恢复（不赌）。
    备份来自旧版本时表结构会缺迁移，恢复仍会执行（数据要紧），但会返回 `needsRestart`，
    提示重启容器由 `prisma migrate deploy` 补齐。
    **恢复图片只补不删**：按文件名补齐，已存在的同名文件（uuid，内容必然一致）跳过，
    绝不删除图片目录里的任何东西——宁可留几个孤儿文件，也不能删掉还有人在引用的图。
    恢复完会核对「库里有引用、盘上没文件」的商品数（`imagesMissing`），不为 0 就在界面直说。
24. **备份目录跟着库文件走**：`<库所在目录>/backups`，容器里就是 `/app/data/backups`，
    和 `suteng.db`、`uploads/` 在同一个挂载卷里，整卷拷走等于把所有备份一起带走。
    注意相对路径的基准：Prisma 把 `file:xxx` 的相对路径解析成**相对 `prisma/` 目录**，
    解析库文件路径时必须跟它一致，否则备份会对着一个不存在的路径干活。
    **图片目录只允许一个算法**：`lib/upload-dir.ts` 的 `uploadDir()`。
    上传接口、读图接口、备份打包三处都引它——以前这三处各自算一遍，
    哪天有人只改了其中一处，备份就会安静地打出一个不含图片的空包。
24.1 **云端存储抽象在 `modules/backup/remote.ts`**，现有两家：
    - `openlist`：老路径，`/api/fs/put`，账号密码换令牌（12h 缓存），上传后回查大小
    - `jianguoyun`：WebDAV（`https://dav.jianguoyun.com/dav`），Basic 认证，
      **账号是邮箱、密码是「应用密码」不是登录密码**；PUT 不会自动建父目录，必须逐级 MKCOL；
      上传用 `fs.openAsBlob` 直接流式发送，几十上百 MB 的包不吃内存
    两家的共同要求：上传成功必须**回查大小**，对不上当失败（网关抖动会 2xx 收一半）。
    加第三家只要在 `remote.ts` 加一个分支，上层 service 不用动。
25. **定时备份的调度器不能挂 `instrumentation.ts`。**
    `instrumentation` 会被 edge 编译，而备份要读整个库文件（`node:fs`），
    不管写成顶层 import 还是「判断 `NEXT_RUNTIME` 后动态 import」，edge 那份 bundle 都会去解析
    `node:path`，构建直接报 `UnhandledSchemeError`（两种写法都试过，都不行）。
    现在挂在 **`/api/health`**：docker-compose 的 healthcheck 每 30 秒打一次，
    是「进程起来后一定会被调用」的唯一位置，跟有没有人打开页面无关。
    `(app)/layout.tsx` 里也点一次作为兜底。`globalThis` 单例保证打一万次也只注册一个定时器。
26. **cron 用「上一个该跑的分钟」判断，不是「记住下次几点」。**
    `prevCronRun(cron, now)` 算出最近一个应触发的分钟，只要 `lastAutoAt < 它` 就跑——
    服务在那一刻没运行（重启、断电、升级）也不会漏，起来后第一次 tick 直接补上。
    反过来「记住下次时间再倒计时」的写法，一旦错过就永远错过，这是刻意不用的原因。
    「今天有没有跑过」不再看日期，而是比分钟：`lastAutoAt >= slot` 就算跑过，
    所以 cron 写成每分钟也不会同一个分钟里重复备份。
27. **网盘上传失败不影响本地备份成功。** 本地快照已经落盘，传不上去只是少一层保险，
    不能把「备份成功」变成「备份失败」。失败记进上传日志 + `backup.lastUploadError`，
    界面给黄条提示与「重传」按钮，审计里也留一句。
28. **上传完必须回查远端文件大小。** R2 / 网关抖动时可能收一半就断还回 200，
    大小对不上就当没传（抛错、不写成功记录）。宁可让人点一次重传，也不能在云上留一份坏文件。
29. **网盘密码与令牌只进不出。** 设置接口返回的是 `passwordSet / tokenSet` 布尔值，
    明文永远不出服务端；表单留空表示「沿用已存的」，所以前端也不可能把明文回填进去。
    取令牌优先用账号密码现换（登录 JWT 48 小时，缓存 12 小时就换新的），
    只在没填密码时才用长期令牌——这样不会出现「令牌过期了，半夜备份传不上去」。
30. **发货工单不是新表，就是出库单的「待发货」阶段。** 判据只有一个：
    `documents.submittedAt` **有值 = 内勤交了、等仓管确认**；空 = 普通草稿。
    不要再加 `status='pending'` 之类的取值——`draft / approved / voided` 这三个值
    被报表、仪表台、红冲、盘点等十几处按 `status` 统计的地方共用，加一个取值就是改一片。
31. **内勤（`clerk`）永远不能审核出库。** 建单接口里 `approveNow` 对 clerk **强制按 false 处理**
    （不是报错，是覆盖）；`approve` 接口的角色白名单里没有 clerk，service 层再拦一道。
    「内勤提交、仓管确认」是整条流程唯一的复核点，只在前端藏按钮等于没拦。
32. **工单隔天确认，记账日要改到今天。** `approveInTx` 里：**有 `submittedAt` 且 `bizDate` 早于今天**
    才把记账日改成今天并写审计；普通草稿不动（仓管补录昨天的发货，那个能力要保留）。
    漏了这一步，昨天报表凭空多一笔、今天的少一笔。
33. **提交工单不动库存。** `submit` 只写 `submittedAt / submittedById` + 审计，
    不产生流水、不扣批次、不碰 `item_instances`。缺货检查只出 `warnings` 给界面做黄字提醒，
    **绝不拦**——硬拦截在仓管点确认那一刻（`approveInTx` 原有的库存校验）。
34. **工单的明细改不了，只能撤销重开。** 只给了 `PATCH /api/outbound/[id]` 改
    `receiverName / trackingNo / externalNo / remark` 四项（都不动货）。
    明细与数量一旦可改，库存校验就得多一套「改前后差额」逻辑，不值得。
    删除接口对 clerk 加了「只能删自己建的」校验，防止互相撤单。
35. **站内跳转一律 `redirectTo()` 相对路径，禁止 `new URL(x, req.nextUrl.origin)`。**
    容器里 `ENV HOSTNAME=0.0.0.0` 是绑卡必须的，但 Next 独立服务器把它当成
    「应用自己的地址」拼 `initURL`（`next-server.js`：`${protocol}://${fetchHostname}:${port}${req.url}`），
    于是路由处理器里 `req.nextUrl.origin` **恒为 `http://0.0.0.0:3000`，从不读 Host 头**。
    用它拼 307 的 Location，浏览器就会被送去一个打不开的地址——局域网 IP、公网域名 +
    反向代理都一样错。相对 Location 由浏览器按当前访问地址解析，端口映射 / 域名 / https 全自动正确。
    2026-10-23 的「每天第一次打开跳到 0.0.0.0:3000」就是这条踩的：访问令牌 8 小时过期，
    隔天首次访问走 `session-refresh` 换令牌，成功分支用 origin 拼了绝对地址。
    **不要用 `experimental.trustHostHeader` 绕过**——它固定拼 `https://`，局域网 http 直接废。
36. **一张出库单 = 一天一批发货，一行 = 一个包裹 = 一个买家。** P11 之后
    「一单一地址」作废：`document_items.receiverInfo / externalNo / trackingNo` 是行级字段，
    **行级留空就回退到单据级** `documents.receiverName / trackingNo / externalNo`。
    回退只做在 `outbound.service.ts` 的 `resolveLine()` 一处，读的地方一律走它，
    不要在 repository 里自己 `?? doc.receiverName`——散在十几处，改一次漏三处。
    老单据、退货挂靠、打印都靠这个回退，所以行级字段**永远可以是空的**，别加 NOT NULL。
37. **发货必须按行确认，`shippedAt` 非空 = 这一行发了。** 判据只看
    `document_items.shippedAt`，不要拿 `documents.status` 推——部分发出的单 `status` 还是 `draft`。
    全部行都发了才 `markApproved`。`ship(id, itemIds)` 里 `itemIds = null` 表示「全部未发行」，
    只对选中的行做库存校验与扣减，**不要为了省事整单扣完再标记**（会多扣没发的行的库存）。
    条件更新 `where shippedAt: null` + 比对影响行数，是防重复发货的唯一手段：
    两个仓管同时点「确认发出」时，第二个必须拿到 409，不能把库存扣两遍。
38. **有行发出去过，就不能整单删除。** `remove()` 里 `shipped > 0` 直接 409。
    删单会级联删明细、而流水挂在单上，库存数字会凭空回来——这比「删不掉」危险得多。
    要作废走红冲。反过来，**没发的行可以单独删**（`removeItem`）：删完 `recountItems()`，
    剩下的行全发了就自动结案。删最后一行要拦——空单没有意义。
39. **打印页在 `(app)` 组之外，零依赖，不引任何库、不生成 PDF。**
    `/print/outbound/[id]` 自己注入 `@page` 的 `size`（A4 / `100mm 150mm`），
    靠 `window.print()` 交给浏览器。同一个路由两种纸靠 `?mode=pick|label` 切换，
    范围靠 `?scope=unshipped|shipped|all`。**按地址分组合并包裹的逻辑只在 `buildGroups()`**
    （`print-sheet.tsx`），改分组规则就改那一处，否则屏幕上的包裹数和纸上的对不上。
    默认 `scope=unshipped`：打印的目的是「拿着去找货」，把发过的打出来只会让人多跑一趟。


## 已知限制

- 账号只能停用、不能删除（单据上的经手人要留着）；停用后无法登录，历史记录不受影响。
- 报表按**业务日期**归月，补录上个月的单会进上个月，不会进本月。
- 导出只有 CSV（UTF-8 BOM），暂不生成 xlsx；需要花哨格式请在 Excel 里另存。
- 库存页的批次与定制件各最多展示 500 条，流水按 50 条分页；超出部分请用搜索或导出。
- 红冲的权限收到管理员 / 店长（`admin` / `manager`），仓管不能冲已生效的账。
- 红冲不校验「原单业务日期是否已结账」：一期没有月结概念，任何时候都能冲。
- 次品区按 SKU 汇总展示，同款多件会并成一行；要看具体件号请展开，或去处置单里勾选。
- 盘点期间**不要补录业务日期早于截止时点的旧单**：那笔会被算成「截止后变动」，
  与已经数进实盘的货重复。补录请等这张盘点单审完再做。
- 良品回架遇到「原出库行跨多个批次」时，只回到**首个批次**（不做按比例拆回）；
  库存合计与批次总量仍然一致，只是归批不精确。
- 出库不校验「客户是否真的付过款」之类业务规则——系统只记数量，不碰钱。
- 单进程内存限流，不适用多实例部署（本项目为单机场景，无影响）。
- 备份本身仍是**单机本地文件**；异地那一层靠云端上传（可关）。
  网盘没配好、或者网盘自己挂了的那段时间，就只剩本机那几份，别把云备份当成必然。
- 定时备份依赖服务进程活着：容器整夜停机就不会有 3 点那份；进程起来后第一次 tick 会**补跑**
  （调度器由 healthcheck 每 30 秒唤起，所以起来 30 秒内就开始工作），
  「今天一定会有一份」成立，只是时间会晚到开机那一刻。
- 网盘只上传、不删除：云端会一直攒着，长期占用空间。现在每份是**整包**——库 + 全部商品图片，
  图片越多包越大（6 张图时约 2.2 MB，库里 6 张时一年版不到 1 GB）；
  要清理请去 OpenList / 坚果云里手动删，系统不会替你动云上的文件。
- 上传是「备份完成后同步传」：网络很慢时那一次备份的接口响应会跟着慢
  （2 MB 左右通常十几秒），图片涨到几百 MB 时会明显变慢——这也是提示「别传原图」的原因之一。
- 恢复是整库覆盖：备份之后新建的账号、改过的密码都会回退，可能被踢回登录页。
  备份来自更早版本时，恢复完需要重启容器让 `prisma migrate deploy` 补齐表结构。
- 恢复期间（几秒）其它请求可能拿到旧连接：请挑没人操作的时段做。
- 备份文件里有全部账（含密码哈希），下载到哪台电脑就要对那台电脑负责，别随手丢在共享盘上。
